Objetivos

La API deberá ser:

RESTful.
Versionada.
Segura.
Consistente.
Fácil de documentar.
Preparada para futuras integraciones (App móvil, Telegram, API pública).

CONTRATO COMÚN DE CATÁLOGOS — Implementado en sprint 4

Todas las rutas anteriores llevan prefijo /api/v1 y requieren sesión JWT.
GET listado: search (hasta 100 caracteres), page (>=1, defecto 1), limit (1–100,
defecto 25), estado (activo/inactivo/todos, defecto activo), sort (nombre/createdAt,
defecto nombre), order (asc/desc, defecto asc). Solo tarifas admite productoId UUID.
El filtro activo de tarifas exige también un producto activo y no borrado.
Las tarifas de productos inactivos pueden administrarse usando estado=todos.

Respuesta del listado: { success: true, data: [...], pagination: { page, limit,
total, totalPages } }. Consulta individual y mutaciones: { success: true, data: {...} }.
GET, PUT y DELETE devuelven 200; POST de alta y reactivación devuelve 201.
Errores: 400 validación, 401 sin sesión, 404 registro inexistente, 409 conflicto.

Cuerpo de alta: nombre obligatorio. Campos específicos: descripcion en productos;
observaciones en referencias; productoId y precio obligatorios en tarifas,
duracionMeses opcional con valor 12; esGratuito opcional (defecto false) en métodos.
PUT admite los mismos campos opcionales y activo. No se aceptan campos ajenos al
catálogo ni valores null. Nombre máximo 100 caracteres, salvo referencias (150);
descripcion y observaciones hasta 2000. Precio entre 0,01 y 99.999.999,99, máximo
dos decimales; producto de una tarifa existente inmutable.

DELETE establece activo=false, nunca borra físicamente. Reactivar establece
activo=true y limpia un deletedAt anterior cuando existe. Altas, cambios y estados
se auditan en la misma transacción. Renombrar un método gratuito conserva su tipo;
un método utilizado no admite cambiar esGratuito.

Paginación

Todos los listados devolverán la misma estructura:

{
  "success": true,
  "data": [],
  "pagination": {
    "page": 1,
    "limit": 25,
    "total": 320,
    "totalPages": 13
  }
}
Filtros

Todos los listados admitirán una estructura homogénea:

?page=1
&limit=25
&search=
&sort=
&order=asc

Además, cada módulo añadirá sus filtros específicos (producto, servidor, fechas, estado, etc.).

Versionado

Toda la API se publicará bajo:

/api/v1

Cuando haya cambios incompatibles se creará:

/api/v2

Así evitaremos romper integraciones existentes.

Mejoras que recomiendo incorporar desde el primer día

Además de lo anterior, añadiría varios aspectos que suelen olvidarse y luego resultan costosos de implementar:

1. Idempotencia

Las operaciones críticas, especialmente las renovaciones y los movimientos financieros, deberían aceptar una clave de idempotencia para evitar registros duplicados si el usuario pulsa el botón dos veces o se repite una petición.

2. Soft Delete consistente

Los endpoints DELETE realizarán siempre borrado lógico. Para restaurar registros, es preferible disponer de endpoints específicos como:

POST /clientes/{id}/restaurar
POST /productos/{id}/reactivar
3. Auditoría automática

Las operaciones de creación, modificación, anulación y restauración registrarán automáticamente:

Usuario.
Fecha y hora.
Acción realizada.
Datos anteriores.
Datos nuevos.
Dirección IP.

Sin que el frontend tenga que enviar esa información.

4. Contratos OpenAPI

Cada endpoint se documentará con:

Parámetros.
Ejemplos de petición.
Ejemplos de respuesta.
Posibles errores.
Esquemas de datos.

Esto permitirá generar clientes para el frontend y una documentación interactiva con Swagger.

ANEXO V1.1 — API de migración desde CLIENTES 2026(Actualizado).xlsx

La importación del Excel será un proceso en dos fases y nunca insertará datos
directamente desde el navegador:

POST /importaciones/clientes/preview

Recibe el archivo como multipart/form-data, calcula su checksum, detecta las
hojas ENE-DIC, valida columnas y crea un staging inmutable para devolver un
resumen sin crear todavía operaciones de negocio:

{
  "success": true,
  "data": {
    "importacionId": "",
    "filas": 2914,
    "clientesNuevos": 0,
    "posiblesDuplicados": 0,
    "errores": 0,
    "advertencias": 0,
    "hojas": []
  }
}

POST /importaciones/:id/confirmar

Confirma una previsualización previamente revisada. Requiere autenticación,
confirmación explícita y una clave de idempotencia. Esta fase crea o relaciona
clientes y deja las filas en staging para la revisión operativa; no crea por sí
sola renovaciones ni movimientos financieros.

GET /importaciones/:id
GET /importaciones/:id/filas
GET /importaciones/:id/errores
GET /importaciones/:id/catalogos
GET /importaciones/:id/valores-pendientes
POST /importaciones/:id/equivalencias
PATCH /importaciones/:id/filas/:filaId/revisar
POST /importaciones/:id/reconciliar

Los seis catálogos gestionables disponen de consulta, alta, edición,
desactivación y reactivación protegidas. Sus rutas y cuerpos están definidos en
CONTRATO COMÚN DE CATÁLOGOS (sprint 4); no requieren cargar una importación.

Permiten consultar el progreso, las filas rechazadas, los conflictos de
identidad y las decisiones tomadas durante la importación. Las equivalencias y
la revisión de cada fila quedan auditadas. La reconciliación solo procesa filas
aceptadas; la creación de renovaciones y movimientos financieros requiere una
confirmación adicional de las reglas contables.

Reglas adicionales para GET /clientes:

Los filtros deberán incluir, cuando el módulo correspondiente esté disponible,
productoId, servidorId, referenciaId, telefono y estadoId. El parámetro sort
solo aceptará una lista blanca de campos y limit tendrá un máximo configurable.

La respuesta de todos los listados usará una única convención: data y el objeto
pagination con page, limit, total y totalPages. Las validaciones del backend
devolverán el mismo formato de error independientemente de que procedan de un
DTO, Prisma o una regla de negocio.
